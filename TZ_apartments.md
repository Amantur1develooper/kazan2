# ТЗ на новую версию модуля «Квартиры» (elnasip_finance)

Версия документа: 1.0 (черновик по факту анализа кода) · Дата: 2026-08-13

## 0. Статус документа

Документ описывает **текущую логику системы «как есть»** — на основе фактического кода
приложения `projects` (модели, импорт/экспорт Excel, расчёты по блокам) и связанного
приложения `finances` (касса, продажи, сметы). Это база для разработчиков новой версии.

В конце каждого раздела, где это уместно, оставлено **место под доработки новой версии**
(`> 🔧 TBD:` — короткие плейсхолдеры, которые нужно заполнить отдельно перед стартом разработки).

## 1. Глоссарий

| Термин | Значение в системе |
|---|---|
| ЖК (Project) | Жилой комплекс — верхний уровень иерархии |
| Блок (Block) | Литер/корпус внутри ЖК, содержит квартиры и смету расходов |
| Квартира (Apartment) | Единица продажи внутри блока |
| Сделка | Продажа квартиры конкретному клиенту (поля `deal_*`, `client_name`) |
| Общаг (CommonCash) | Единая касса компании (одна запись в БД), в неё стекаются все поступления |
| Смета (EstimateItem) | Плановая статья расходов блока (материал/работа) |
| Выделение (Allocation) | Выдача денег из Общага на конкретную позицию сметы |

---

## 2. Иерархия данных

```
Project (ЖК)
 └── Block (Блок/литер) — своя смета, своя плановая цена м²
      └── Apartment (Квартира)
           ├── DealPayment (платежи по сделке продажи)
           ├── RentPayment (платежи по аренде)
           └── ApartmentComment (комментарии/история)
```

Продажа квартиры отдельно порождает запись `finances.Sale`, которая является
триггером для зачисления денег в `CommonCash` через `CashFlow` (см. раздел 8).

### 3.2 Block (Блок/литер)

| Поле | Тип | Назначение |
|---|---|---|
| `project` | FK → Project | Принадлежность к ЖК |
| `name` | строка | Название/литер блока |
| `floors` | int | Количество этажей |
| `total_area`, `sold_area` | Decimal (поля модели) | ⚠️ см. нюанс в разделе 13.2 — фактически перекрыты одноимёнными `@property` |
| `planned_price_per_m2` | Decimal | Плановая цена за м² по блоку (применяется массово к свободным квартирам, см. 7.4) |

Ключевые вычисляемые свойства (используются в разделе 8):
`received_amount`, `sold_area_sum`, `not_sold_area_sum`, `calc_total_area`,
`calc_sold_area`, `remaining_area`, `total_discount`, `sold_apartments_count`,
`not_sold_minus_allocated`, `get_allocated_sum()`.

### 3.3 Apartment (Квартира)

| Поле | Тип | Обязательность | Назначение |
|---|---|---|---|
| `block` | FK → Block | да | Принадлежность |
| `floor` | int | да | Этаж |
| `apartment_number` | строка | да | Номер (уникален в рамках блока) |
| `rooms` | int | да | Количество комнат |
| `area` | Decimal | да | Проектная площадь, м² |
| `sold_area` | Decimal | авто | Проданная площадь — считается из суммы платежей / факт. цену м² |
| `is_sold` | bool | авто/вручную | Статус «продана» |
| `is_reserved` | bool | вручную | Статус «бронь» |
| `is_barter` | bool | из импорта | Статус «бартер» |
| `is_rented` | bool | вручную | Статус «в аренде» |
| `planned_price_per_m2` | Decimal | да | Плановая цена за м² (до продажи) |
| `planned_deal_amount` | Decimal | авто | `area * planned_price_per_m2`; обнуляется, как только `is_sold=True` |
| `fact_price_per_m2` | Decimal | при продаже | Фактическая цена за м² сделки |
| `deal_Fakt_deal_amount` | Decimal | при продаже | Сумма договора (цена сделки) |
| `deal_amount` | Decimal | авто | Фактически поступило денег по сделке |
| `remaining_deal_amount` | Decimal | авто | Остаток к оплате по сделке |
| `discount` | Decimal | опц. | Скидка в сомах, применяется один раз при продаже (см. 7.2) |
| `deal_number` | строка | опц. | Номер сделки |
| `client_name` | строка | при продаже/брони | ФИО клиента |
| `is_rented`, `rent_price_per_month`, `rent_start_date`, `rent_end_date`, `tenant_name`, `tenant_phone`, `tenant_contract` | — | опц. | Блок полей аренды (см. раздел 9) |

Вычисляемые свойства: `rent_status`, `total_rent_income`, `sold_area_if_sold`,
`calculated_price` (`area * planned_price_per_m2`), `deal_amount_if_sold`.

### 3.4 DealPayment (платёж по сделке продажи)

Каждый платёж клиента фиксируется отдельной записью. При сохранении **пересчитывает
квартиру целиком** (см. формулы в разделе 7.3):
- `apartment.deal_amount` = сумма всех платежей по квартире;
- `apartment.remaining_deal_amount` = `deal_Fakt_deal_amount − сумма платежей` (не ниже 0);
- `apartment.sold_area` = `сумма платежей / fact_price_per_m2` (не больше `area`);
- `apartment.is_sold` выставляется в `True`, если сумма платежей > 0 или задан `deal_Fakt_deal_amount` > 0 — **и никогда не сбрасывается обратно** (см. 13.3).

### 3.5 RentPayment (платёж по аренде)

Независимая от продажи ветка. При первом платеже создаёт `CashFlow` (приход в Общаг)
и выставляет `apartment.is_rented = True`.

### 3.6 ApartmentComment

Свободный текстовый комментарий/лог по квартире — используется как ручными
пользователями, так и автоматически при импорте Excel (см. 9.6).

## 4. Статусы квартиры и их совместимость

Статус квартиры — это комбинация независимых булевых флагов, а не единое поле:

| Статус в UI | Условие |
|---|---|
| Свободна | `is_sold=False`, `is_reserved=False`, `is_rented=False` |
| Бронь | `is_reserved=True`, `is_sold=False` |
| Продана | `is_sold=True` |
| Аренда | `is_rented=True` |
| Бартер | `is_barter=True` (всегда сопровождается `is_sold=True`) |

Автоматические переходы (в `Apartment.save()`):
- квартира продана (`is_sold=True`) → снимается аренда (`is_rented`, даты аренды обнуляются);
- квартира сдана в аренду (`is_rented=True`) → снимается бронь (`is_reserved=False`);
- квартира продана → `planned_deal_amount` принудительно обнуляется.

> `is_reserved=True` одновременно технически возможны через прямое редактирование).

## 5. Как формируются квартиры (3 способа создания)

1. **Вручную, по одной** — форма добавления квартиры в блок (`apartment_add` /
   `add_apartment`, обязательны: номер, комнаты, площадь, плановая цена м², этаж).
2. **Массовый импорт из Excel по блоку** — основной способ первоначального наполнения
   и синхронизации (раздел 6).
3. **Массовое удаление всех квартир блока** (`delete_block_apartments`) — используется
   перед повторной полной загрузкой блока из Excel.

Плановая цена за м² может быть выставлена **массово на весь блок** одной операцией
(`set_block_price`): применяется только к квартирам, которые ещё не проданы и не
бартер (`is_sold=False, is_barter=False`), пересчитывая `planned_price_per_m2`,
`fact_price_per_m2` и `planned_deal_amount` разом.

## 6. Импорт квартир из Excel

### 6.1 Поддерживаемые форматы

`.xlsx` (через `openpyxl`) и `.xls` (через `xlrd`, устаревший формат — используется
реальными файлами компании, пример: `ЭКО А.xls`). Оба формата приводятся к единому
интерфейсу листа перед разбором.

### 6.2 Структура файла (лист 1, первая строка — заголовки)

Полный перечень колонок, встречающихся в реальном файле `ЭКО А.xls` (17 колонок).
Порядок колонок не важен — сопоставление идёт **по названию заголовка**, не по индексу.

| № | Заголовок колонки | Обязательна | Используется как | Пример из файла |
|---|---|:---:|---|---|
| 1 | `№` | нет | не используется импортом | 1 |
| 2 | `Этаж` | нет | `floor` (по умолчанию 1) | 2 |
| 3 | `Строительный объект` | нет | не используется импортом | Ж.К. Эко-Парк |
| 4 | `Предварительный номер` | **да** | `apartment_number` — ключ поиска квартиры в блоке (текст после `(` отсекается) | А-7.2.2 |
| 5 | `Количество комнат` | **да** | `rooms` | 1 |
| 6 | `Общая площадь ориентировочно` | **да** | `area` | 49.5 |
| 7 | `Дата договора` | нет | парсится, но **никуда не сохраняется** (см. нюанс 13.7) | 26-01-2026 |
| 8 | `Ф.И.О.` | нет | `client_name`; пусто = квартира свободна/возврат | Тургунбаев Т. А. |
| 9 | `Цена за 1 м.кв.` | нет | `fact_price_per_m2` и `planned_price_per_m2` | 78000 |
| 10 | `Сумма договора` | нет | `deal_Fakt_deal_amount` | 3 861 000 |
| 11 | `Оплачено` | нет | `deal_amount` (сколько поступило) | 2 794 400 |
| 12 | `Остаток на оплату` | нет | `remaining_deal_amount`; если пусто — считается как `Сумма договора − Оплачено` | 1 066 600 |
| 13 | `Телефон` | нет | попадает только в комментарий (см. 13.8) | 077 124 68 08 |
| 14 | `Примечание` | нет | попадает в комментарий к квартире | текст |
| 15 | `Тип сделки` | нет | определяет `is_barter` / `is_reserved` (см. 6.3) | Обычный / Бронь / Бартер |
| 16 | `Тип клиента` | нет | не используется импортом | Свой |
| 17 | `Куратор ОП` | нет | не используется импортом | Минура |

Форматы даты в `Дата договора`, которые парсятся: `дд-мм-гггг`, `дд.мм.гггг`, `гггг-мм-дд`.
Суммы принимают как числа, так и текст с пробелами/запятыми (`"2 794 400,00"` → 2794400.00).

### 6.3 Определение статуса по колонке «Тип сделки»

| Значение содержит | Итоговый статус |
|---|---|
| «бартер» (без учёта регистра) | `is_barter=True`, `is_sold=True`, `is_reserved=False` |
| «брон» (и не бартер) | `is_reserved=True`, `is_sold=False` (деньги всё равно учитываются) |
| иное / пусто | `is_sold = (есть ФИО) OR (Оплачено > 0)` |

### 6.4 Правила сопоставления строки с БД

Ключ поиска: пара `(block, apartment_number)`. Строка без номера — пропускается
(`skipped`). Флаги формы импорта:
- **Обновлять существующие** (`update_existing`, по умолчанию включено);
- **Создавать отсутствующие** (`create_missing`, по умолчанию включено).

### 6.5 Особые события при повторном импорте (детектор изменений)

При каждом повторном импорте система сравнивает состояние БД и Excel и помечает
особые случаи (попадают в лог результатов и в комментарий к квартире):

| Событие | Условие обнаружения | Действие |
|---|---|---|
| **ВОЗВРАТ** | в БД `is_sold=True`, в Excel — ФИО пусто, бронь не указана, `Оплачено=0` | `is_sold=False`, `client_name=None`, `is_reserved=False` |
| **ПЕРЕПРОДАЖА** | в БД и в Excel указано ФИО, но они различаются (без учёта регистра/пробелов) | обновляется `client_name`, финансовые поля перезаписываются из Excel |
| **БАРТЕР** | `Тип сделки` содержит «бартер» | статус выставляется как бартерная продажа |
| **БРОНЬ+ОПЛАТА** | `Тип сделки` = бронь и `Оплачено > 0` | пишутся финансовые поля, но `planned_deal_amount=0` (сделка уже идёт) |

### 6.6 Что импорт делает и чего НЕ делает

- Пишет финансовые поля квартиры **напрямую** (`update()` по queryset), **в обход**
  `Apartment.save()` — поэтому автоматические пересчёты и переходы статусов
  из раздела 4 при импорте **не срабатывают**.
- **Не создаёт** записи `DealPayment` и `Sale` — соответственно, импорт **не проводит
  деньги через `CommonCash`/`CashFlow`**. Импорт обновляет только карточку квартиры,
  а не движение денег в общей кассе.
- Каждая строка обрабатывается в отдельной транзакции — ошибка одной строки не
  прерывает импорт остальных, а попадает в список `errors` с номером строки.

### 6.7 Итоговый отчёт после импорта

Пользователю показываются агрегаты: создано / обновлено / пропущено, количество
возвратов / перепродаж / бартеров, подробный построчный лог событий и список ошибок
по строкам (`Строка N (номер квартиры): текст ошибки`).

## 7. Продажа квартиры и учёт суммы сделки

Продажа — двухшаговый ручной процесс (в UI это два разных экрана):

### 7.1 Шаг 1 — оформление сделки (`sell_apartment`)

Доступно только для ещё не проданной квартиры. Пользователь вводит:
`fact_price_per_m2` (факт. цена за м²), `discount` (скидка в сомах), `client_name`,
`deal_number`.

Расчёт суммы договора при сохранении:

```
deal_Fakt_deal_amount = area * fact_price_per_m2 − discount
remaining_deal_amount = deal_Fakt_deal_amount   (платежей ещё не было)
is_sold = True
```

На этом шаге **деньги в кассу не поступают** — это только фиксация условий сделки.

### 7.2 Скидка (`discount`)

Скидка в сомах учитывается **один-единственный раз**, в момент шага 7.1, вычитаясь
из суммы договора. Дальше в системе она нигде не пересчитывается и не валидируется
(можно указать скидку больше суммы договора — отрицательная сумма договора не
блокируется формой).

### 7.3 Шаг 2 — регистрация платежей (`add_payment` → `DealPayment`)

Каждое реальное поступление денег от клиента фиксируется отдельным платежом.
При сохранении платежа:

```
deal_amount              = Σ(все платежи по квартире)
remaining_deal_amount    = max(deal_Fakt_deal_amount − Σ(платежи), 0)
sold_area                = min(Σ(платежи) / fact_price_per_m2, area)
is_sold                  = True   (если Σ(платежи) > 0 или deal_Fakt_deal_amount > 0)
```

Одновременно с созданием `DealPayment` система создаёт запись `finances.Sale`
(`amount = сумма платежа`, `area = 0`, `apartment`, `block`), которая при сохранении
сама создаёт `CashFlow(flow_type='income')` и увеличивает баланс `CommonCash`.
**Именно через эту цепочку сумма продажи квартиры физически попадает в общую кассу.**

### 7.4 Как сумма продажи указывается/агрегируется на уровне блока

На уровне блока (`Block`) отдельного поля «сумма продаж» нет — оно **всегда
вычисляется на лету** через агрегирующие свойства:

| Свойство блока | Формула |
|---|---|
| `received_amount` | Σ `deal_amount` по квартирам блока, где `is_sold=True` — это и есть «сумма продажи квартир в блоке», сколько денег реально поступило |
| `sold_area_sum` | Σ `area` по квартирам блока, где `is_sold=True` |
| `not_sold_area_sum` | Σ `area` по квартирам, где `is_sold=False AND is_barter=False` (бронь считается свободной площадью) |
| `total_discount` | Σ `discount` по всем квартирам блока |
| `not_sold_minus_allocated` | `received_amount − get_allocated_sum()` (сколько из поступивших денег ещё не распределено по смете) |

На уровне ЖК (`Project`) аналогично: `total_received_amount` = сумма `received_amount`
по всем блокам ЖК; `calc_sold_area` / `calc_total_area` — по всем квартирам ЖК.

Дополнительно на экране блока (`block_detail`) считаются:
- `fakt_prodaj` — Σ `deal_Fakt_deal_amount` по проданным квартирам (сумма договоров, а не фактически полученных денег);
- «план продаж» (`plan_prodaj`) — Σ `area * planned_price_per_m2` (либо цена блока, если у квартиры своя не задана) по всем непроданным и небартерным квартирам, включая бронь.

## 9. Аренда квартир (отдельная ветка, не путать с продажей)

Поля: `is_rented`, `rent_price_per_month`, `rent_start_date`, `rent_end_date`,
`tenant_name`, `tenant_phone`, `tenant_contract`. Платежи — отдельная модель
`RentPayment`, каждый платёж создаёт приход в `CashFlow`/`CommonCash` напрямую
(без модели `Sale`). Продажа квартиры автоматически снимает её с аренды (раздел 4).

## 10. Экспорт в Excel — два независимых, несовместимых формата

### 10.1 Экспорт по блоку, реимпортируемый (`export_block_apartments_excel`)

12 колонок, названия заголовков **совпадают 1-в-1** с форматом импорта (раздел 6.2),
поэтому выгруженный файл можно поправить в Excel и загрузить обратно. Поддерживает
фильтры через GET-параметры: `only_free`, `only_rented`, `only_sold`, `only_reserved`.

Нюансы данного экспорта:
- `Дата договора` заполняется как `apartment.created_at` (дата создания записи в БД),
  а не реальная дата подписания договора — отдельного поля для неё в модели нет;
- `Телефон` всегда экспортируется пустым — в модели квартиры нет поля телефона
  покупателя (есть только `tenant_phone` для арендатора);
- `Примечание` формируется из пометки «бронь» (если применимо) + текст последнего
  комментария к квартире (обрезается до 200 символов).

### 10.2 Общий отчётный экспорт по всем ЖК (`export_apartments_xlsx`, из списка `/apartments/`)

16 колонок, **другой набор заголовков** (`'ЖК', 'Блок', 'Этаж', 'Номер', …`),
ориентирован на аналитику/отчётность, а не на обратную загрузку. Экспортирует
результат текущей фильтрации из формы списка квартир (`ApartmentFilterForm`:
проект, блок, статус, комнаты, площадь, цена, этаж, поиск по клиенту).

### 10.3 Важный нюанс

Форматы 10.1 и 10.2 **несовместимы между собой** — файл из общего отчётного экспорта
нельзя загрузить обратно через импорт блока (другие заголовки колонок). Разработчикам
новой версии нужно явно решить, нужен ли единый формат обмена.

## 12. Известные технические нюансы и несоответствия (важно учесть при переписывании)

1. **Двойной путь зачисления денег.** Деньги от продажи попадают в `CommonCash`
   только через ручной ввод платежа (`add_payment` → `Sale`); импорт Excel их туда
   не проводит (раздел 8).
2. **`Block.total_area` / `Block.sold_area` объявлены дважды** — сначала как обычные
   поля модели (со значениями по умолчанию 100 и 1 соответственно), затем в этом же
   классе повторно как `@property` с тем же именем. Python-property побеждает при
   обращении к атрибуту, поля в БД фактически «мёртвые» и не используются напрямую.
3. **`is_sold` никогда не сбрасывается в `False` в `DealPayment.save()`** — даже если
   удалить все платежи по квартире, статус «продана» останется (комментарий в коде:
   «никогда не сбрасываем»). Единственный способ вернуть квартиру в «свободна» —
   через специальную логику «ВОЗВРАТ» при повторном импорте Excel (раздел 6.5) или
   правку статуса вручную в админке.
4. **Скидка учитывается один раз и не валидируется** (раздел 7.2).
5. **`planned_deal_amount` безвозвратно обнуляется**, как только квартира помечена
   проданной — использовать это поле для анализа «план vs факт» по уже проданным
   квартирам нельзя, исторические плановые цифры теряются.
6. **Два разных списка квартир** с похожими именами и разной логикой:
   `views.apartment_list(block_id)` (постраничный список по одному блоку) и
   `apartmentsviews.apartment_list(request)` (сквозной список по всем ЖК с фильтрами
   и своим экспортом) — риск путаницы при доработке.
7. **Два несовместимых формата Excel-экспорта** (раздел 10.3).
8. **Проверка ролей отключена** на продаже квартиры (раздел 11).
9. **«Дата договора» не хранится как поле** — при экспорте подставляется дата
   создания записи в БД, что искажает реальную дату сделки при цикле
   экспорт → правка → повторный импорт.
10. **Телефон покупателя не хранится как отдельное поле** — попадает только в
    свободный текст комментария при импорте и не может быть надёжно извлечён обратно
    или отредактирован через форму.
11. **`finances.Sale.area` всегда пишется как `0`** при создании из `add_payment` —
    само поле `area` в модели `Sale` по факту не используется по назначению.
12. **Импорт разрешает случайный «возврат»**: если в Excel-файле у ранее проданной
    квартиры случайно стёрли ФИО (не по злому умыслу, а опечаткой), при `Оплачено=0`
    система интерпретирует это как реальный возврат и снимает продажу.
